# Social engine rule decisions

This document records the Phase 2 social-card decisions that are implemented in the authoritative reducer, and it marks where the canonical Bible v5 was not detailed enough to lock every edge case yet.

The Bible v5 PDF is not stored in this repository. The social engine therefore uses the supplied Phase 2 brief plus the approved V4 reference template as the working source set, and it treats anything not explicitly implemented here as deferred.

| Prompt eligibility | Phase 2 brief, approved V4 metadata model | Eligibility checks family, content world, target scope, group size range (`groupSizeMin` / `groupSizeMax`), stage, intensity, language, call suitability, repeat group, and anti-repeat metadata before a prompt can be selected. Deterministic selection chooses the lexicographically first eligible prompt id. | Selection metadata stays server-side; only the selected prompt snapshot is exposed to the triggering player. | Yes, via `GameCommandContext` prompt pool/profile | HIGH | Future prompt services may add richer stage and moderation filters |
| Content-world enforcement | Phase 2 brief | `GameConfig.contentWorld` is authoritative and prompt selection rejects prompts whose world does not match the session. | Server-side only | Yes | HIGH | The repository still needs the broader room/profile wiring that will populate this in production |
| Paranoia Hybrid Locked flow | Phase 2 brief plus verified legacy Web Hybrid Locked behavior | Paranoia enters prompt selection, then target selection. `SELECT_PARANOIA_TARGET` is accepted only from the triggering player and stores the initial target separately from later answer-player state. `SELECT_PARANOIA_PHASE` chooses Classic or Stranger without resolving the card. Classic requires the initial target to choose another answer player through `SELECT_PARANOIA_CLASSIC_ANSWER`; only that named player can resolve with `SUBMIT_PARANOIA_CLASSIC_DECISION` as `REVEAL` or `KEEP_SECRET`. Classic `REVEAL` is `PUBLIC` and may carry prompt text; `KEEP_SECRET` is private and does not carry prompt text. Stranger vote submissions are private; vote resolution is public and count-based. | No | HIGH | Presentation copy and transport projections still need end-to-end runtime verification outside the pure reducer |
| Duel target and question selection | Phase 2 brief, legacy compatibility runtime, and locked Duel prompt model | Duel enters a pending target-selection state and accepts `SELECT_DUEL_TARGET` only from the triggering player. The legacy Web runtime then requires explicit Manual or Duel Roulette question-source selection and a challenger-selected fixed Duel timer before response windows begin. Manual/team-created Duel questions reuse the existing prompt storage path with `type='duel'`, `targeting='specific'`, and `duelJudgingMode='GROUP_VOTE'`; Duel Roulette selects one eligible shared Duel question from `type='duel'` prompts rather than Truth/Dare pools. The canonical reducer still attaches the eligible Duel question during target selection until prompt-source commands are promoted there, but it stores that same shared question on `pendingDuel.prompt` for both participants and no longer opens a Nope reaction window because Duel cannot be Noped. | Target and prompt-selection metadata are `PLAYER_PRIVATE`. | No | HIGH | Shared-engine prompt-source and fixed timer commands remain the next canonical convergence step |
| Duel response tracking and winner resolution | Phase 2 brief plus locked Duel resolution rule | The reducer tracks initiator response, opponent response, and resolution readiness against the same `pendingDuel.prompt`. Once both responses exist, subjective Duel questions open an eligible non-participant group vote; Duel participants cannot vote on or directly choose their own winner. A unique top vote awards the local Duel recap win, while ties or no eligible submitted votes award no Duel winner. Current Duel prompt content has no structured objective answer/evaluation metadata, so game-provided text prompts still use group vote rather than fake automatic judging. `SocialPrompt.duelJudgingMode` and optional `duelObjectiveEvaluation` now provide the future contract boundary for objectively judgeable app Duel content. | Response metadata is private to the involved players. Vote submissions are private to the voter; vote resolution is public and count-based. | No | HIGH | Automatic app-enforced Duel judging requires real structured Duel answer/evaluation content and evaluator implementation |
| Chaos approved catalogue | `Game_rules.md` sections 24–26 | Chaos no longer opens a generic all-player prompt. The shared reducer resolves the approved catalogue slices implemented in Phase 4: Blind Swap transfers up to three cards simultaneously without triggering transferred forced-on-draw cards, and Reverse Order flips direction while recording `GameState.chaosReverseActive`. | Chaos effect selection/resolution events are public gameplay state; no prompt text is generated. | No for the approved catalogue shape; deterministic selection uses game seed/revision/card id | HIGH for Blind Swap and Reverse Order | Additional Chaos effects beyond Blind Swap and Reverse Order remain unresolved in `Game_rules.md` and must not be invented |
| Narrow Nope reaction | `Game_rules.md` section 37 | Nope is a dedicated reaction command. Current locked eligibility is narrow: the affected Truth/Dare player may use an owned real Nope, including when that affected player is the selected target rather than the actor. Duel and other families remain fail-closed unless explicitly approved. `projectDecisionCapabilities()` now exposes eligible `PLAY_NOPE` options so Web and Telegram submit the shared command rather than calculating local reaction windows. | Nope rejection metadata is private to the command submitter; successful cancellation uses normal social-resolution visibility. | No | HIGH for Truth/Dare affected-player eligibility and Duel rejection | Whether Truth or Chaos or any other family can be Noped remains unresolved in `Game_rules.md` |
| Answer state machine | Phase 3B brief, approved V4 reference, and `docs/answer-mode-rule-decisions.md` | The reducer models `WAITING`, `MODE_SELECTED`, `REVIEW`, and `SUBMITTED` answer paths. `SELECT_ANSWER_MODE`, `REVIEW_ANSWER`, `SUBMIT_ANSWER`, `SUBMIT_CHOICE`, and `MARK_ANSWERED_LIVE` are now authoritative answer controls. `CAPTURING` remains a client-side presentation concept rather than an engine state. | Answer draft and review state remain server-side until final resolution. | Yes, through the explicit answer mode | HIGH | Timer behavior is now covered by `docs/timer-timeout-rule-decisions.md` |
| Turn advancement after social resolution | Phase 2 brief | Social effects do not advance the turn until the required prompt/target/reaction work is complete. Once resolved, the engine either advances one turn or confirms a win if the active player emptied their hand legally. | Public resolution events plus any private command metadata needed by the projection layer. | No | HIGH | The exact presentation layer for unresolved social effects is still a later-phase concern |
| Event privacy | Phase 1 and Phase 2 brief | Private social events carry recipient player ids so the later projection layer can filter them before transport. Public events never contain private target or answer content. | `PUBLIC` / `PLAYER_PRIVATE` | No | HIGH | The Socket.IO projection layer still needs to enforce the visibility rules |
| ROULETTE PRESENTATION CONTRACT | Phase 2 brief and Canonical Master Bible v5 roulette invariant | `SocialState.roulettePresentation` stores a deterministic presentation id, selected result, eligible candidate ids, presentation type, and optional deterministic seed. The selected result is created by the engine before any client presentation. No animation or live countdown loop runs in the engine; authoritative timer deadline metadata and timeout resolution live in `docs/timer-timeout-rule-decisions.md`. | Presentation events are `PLAYER_PRIVATE` for selected prompt/target data. A `SEALED` projection omits `selectedResultId`; public events do not carry it. | No | CANONICAL invariant; presentation details are provisional | Client duration, labels, animation choreography, and countdown UI remain open |
| AUTHORSHIP MODES | Existing `AuthorshipMode` contract and Phase 2 brief | `SIGNED` reveals the server-retained author when supplied; `REVEAL_AFTER` retains the author while sealed; `TABOO` keeps the author anonymous. The engine does not invent additional modes. | Author ids are stored in `SocialState.authorship` but only projected when the reveal state permits it. | Yes, via prompt metadata and server-supplied author mapping | CANONICAL modes; reveal timing is provisional/deferred | Exact publishing and reveal conditions are not locked |
| AUTHORSHIP REVEAL STATE | Phase 2 brief and privacy boundary | `SocialAuthorshipState.revealState` is explicit as `SEALED` or `REVEALED`. Signed authorship is immediately revealable; `REVEAL_AFTER` has no reveal command in this slice; `TABOO` remains anonymous. | `projectAuthorship` excludes `authorPlayerId` while sealed or taboo. No public social event includes the retained author id. | No | CANONICAL privacy boundary; trigger is DEFERRED | A future authoritative condition may transition `REVEAL_AFTER` to `REVEALED` |
| SEALED RESULT PRIVACY | REQUIREMENTS.md R3/R14 and Phase 2 brief | `SEALED` means the presentation-safe projection omits both `selectedResultId` and candidate metadata, so the selected result is not directly or indirectly inferable. Authoritative candidates remain server-side. Clients cannot replace the engine-selected result because no result-submission command exists. | Public/safe projections contain neither the sealed result nor a narrowing singleton candidate list; private projections carry only the recipients allowed by the social effect. | No | HIGH | The eventual transport projection must preserve this filtering |

- Full authorship reveal workflow and any `REVEAL_AFTER` trigger
- Additional Chaos custom effects beyond Blind Swap and Reverse Order
- Objective Duel answer/evaluation content for automatic app-enforced judging
- Timer deadline metadata and timeout resolution are implemented in `docs/timer-timeout-rule-decisions.md`; client countdown presentation remains deferred
- Live Railway/client deployment and browser click-through verification remain Phase 8
