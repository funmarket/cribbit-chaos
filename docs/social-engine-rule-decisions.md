# Social engine rule decisions

This document records the Phase 2 social-card decisions that are implemented in the authoritative reducer, and it marks where the canonical Bible v5 was not detailed enough to lock every edge case yet.

The Bible v5 PDF is not stored in this repository. The social engine therefore uses the supplied Phase 2 brief plus the approved V4 reference template as the working source set, and it treats anything not explicitly implemented here as deferred.

| Rule | Source | Implementation | Visibility | Configurable? | Confidence | Open question |
| --- | --- | --- | --- | --- | --- | --- |
| Truth card entry | Phase 2 brief, approved V4 prompt flow | Playing Truth consumes the card, selects an eligible prompt deterministically from the supplied prompt pool or supplied selected prompt, stores `social.promptSelection`, and blocks normal play/draw until resolved. | Prompt selection is `PLAYER_PRIVATE`; trigger and answer-required markers remain `PUBLIC`. | Yes, via prompt pool and prompt profile input | HIGH | None for this slice |
| Dare card entry | Phase 2 brief, approved V4 prompt flow | Playing Dare uses the same authoritative prompt-selection boundary as Truth and enters the same pending answer state. | Prompt selection is `PLAYER_PRIVATE`; trigger and answer-required markers remain `PUBLIC`. | Yes, via prompt pool and prompt profile input | HIGH | None for this slice |
| Prompt eligibility | Phase 2 brief, approved V4 metadata model | Eligibility checks family, content world, target scope, group size range (`groupSizeMin` / `groupSizeMax`), stage, intensity, language, call suitability, repeat group, and anti-repeat metadata before a prompt can be selected. Deterministic selection chooses the lexicographically first eligible prompt id. | Selection metadata stays server-side; only the selected prompt snapshot is exposed to the triggering player. | Yes, via `GameCommandContext` prompt pool/profile | HIGH | Future prompt services may add richer stage and moderation filters |
| Content-world enforcement | Phase 2 brief | `GameConfig.contentWorld` is authoritative and prompt selection rejects prompts whose world does not match the session. | Server-side only | Yes | HIGH | The repository still needs the broader room/profile wiring that will populate this in production |
| Paranoia target selection | Phase 2 brief, legacy compatibility runtime | Paranoia enters a pending target-selection state and accepts `SELECT_PARANOIA_TARGET` only from the triggering player. Invalid or self-targets are rejected. | Target selection is `PLAYER_PRIVATE`. | No | HIGH | No authored reveal contract beyond the private target choice was specified for this slice |
| Duel target selection | Phase 2 brief, legacy compatibility runtime | Duel enters a pending target-selection state and accepts `SELECT_DUEL_TARGET` only from the triggering player. The target selection then attaches an eligible Duel prompt and, if appropriate, opens a Nope reaction window. The window remains open until the affected opponent explicitly responds or plays Nope. | Target and prompt-selection metadata are `PLAYER_PRIVATE`. | No | HIGH | Winner scoring and voting semantics remain deferred |
| Duel response tracking | Phase 2 brief | The reducer tracks initiator response, opponent response, and resolution readiness, but it does not invent a scoring model. Once both responses exist, the turn can advance. | Response metadata is private to the involved players. | No | MEDIUM | Canonical winner determination was not locked in the supplied brief |
| Chaos entry | Phase 2 brief | Chaos now supports the generic social-effect state, including prompt selection and answer resolution. For `targeting='all'`, the engine tracks every required participant and resolves only after each one completes; this slice does not implement a general-purpose Chaos scripting system. | Prompt selection is private to the triggering player. | Yes, via supplied prompt pool | MEDIUM | Custom Chaos effect families and target-subset behaviors remain deferred unless later canonicalized |
| Nope reaction | Phase 2 brief, approved V4 reference, legacy runtime notes | Nope is a dedicated reaction command. In this slice it is supported for the Duel reaction window, consumes the Nope card exactly once, and blocks the eligible effect. The reaction window stays open if the initiator responds first and closes when the affected opponent responds or implicitly declines. | Nope reaction metadata is private to the involved players. | No | HIGH | Whether additional social effects should become Nope-eligible is intentionally left open |
| Answer state machine | Phase 2 brief, approved V4 reference | The reducer models `WAITING`, `MODE_SELECTED`, `CAPTURING`, `REVIEW`, and `SUBMITTED` paths through `GameState.social.answerState`. `SELECT_ANSWER_MODE`, `REVIEW_ANSWER`, `SUBMIT_ANSWER`, `SUBMIT_CHOICE`, and `MARK_ANSWERED_LIVE` are supported where appropriate. | Answer draft and review state remain server-side until final resolution. | Yes, through the explicit answer mode | HIGH | Passive transcript capture and microphone input remain deferred |
| Turn advancement after social resolution | Phase 2 brief | Social effects do not advance the turn until the required prompt/target/reaction work is complete. Once resolved, the engine either advances one turn or confirms a win if the active player emptied their hand legally. | Public resolution events plus any private command metadata needed by the projection layer. | No | HIGH | The exact presentation layer for unresolved social effects is still a later-phase concern |
| Event privacy | Phase 1 and Phase 2 brief | Private social events carry recipient player ids so the later projection layer can filter them before transport. Public events never contain private target or answer content. | `PUBLIC` / `PLAYER_PRIVATE` | No | HIGH | The Socket.IO projection layer still needs to enforce the visibility rules |
| ROULETTE PRESENTATION CONTRACT | Phase 2 brief and Canonical Master Bible v5 roulette invariant | `SocialState.roulettePresentation` stores a deterministic presentation id, selected result, eligible candidate ids, presentation type, and optional deterministic seed. The selected result is created by the engine before any client presentation. No animation or timer runs in the engine. | Presentation events are `PLAYER_PRIVATE` for selected prompt/target data. A `SEALED` projection omits `selectedResultId`; public events do not carry it. | No | CANONICAL invariant; presentation details are provisional | Client duration, labels, and animation choreography remain open |
| AUTHORSHIP MODES | Existing `AuthorshipMode` contract and Phase 2 brief | `SIGNED` reveals the server-retained author when supplied; `REVEAL_AFTER` retains the author while sealed; `TABOO` keeps the author anonymous. The engine does not invent additional modes. | Author ids are stored in `SocialState.authorship` but only projected when the reveal state permits it. | Yes, via prompt metadata and server-supplied author mapping | CANONICAL modes; reveal timing is provisional/deferred | Exact publishing and reveal conditions are not locked |
| AUTHORSHIP REVEAL STATE | Phase 2 brief and privacy boundary | `SocialAuthorshipState.revealState` is explicit as `SEALED` or `REVEALED`. Signed authorship is immediately revealable; `REVEAL_AFTER` has no reveal command in this slice; `TABOO` remains anonymous. | `projectAuthorship` excludes `authorPlayerId` while sealed or taboo. No public social event includes the retained author id. | No | CANONICAL privacy boundary; trigger is DEFERRED | A future authoritative condition may transition `REVEAL_AFTER` to `REVEALED` |
| SEALED RESULT PRIVACY | REQUIREMENTS.md R3/R14 and Phase 2 brief | `SEALED` means the presentation-safe projection omits both `selectedResultId` and candidate metadata, so the selected result is not directly or indirectly inferable. Authoritative candidates remain server-side. Clients cannot replace the engine-selected result because no result-submission command exists. | Public/safe projections contain neither the sealed result nor a narrowing singleton candidate list; private projections carry only the recipients allowed by the social effect. | No | HIGH | The eventual transport projection must preserve this filtering |

## Deferred by design

- Full authorship reveal workflow and any `REVEAL_AFTER` trigger
- Other Chaos custom effects beyond the generic state contract
- Duel scoring / winner determination
- Pass / Rewind / Flag / Speak / Type / Choose / Answered Live transport behavior beyond reducer state
- Phase 3 moderation and safety behavior
- Multiplayer transport wiring
